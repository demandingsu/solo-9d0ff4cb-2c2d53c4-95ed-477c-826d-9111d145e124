# 采购标段截标时间核验工具

面向投标专员的网页工具：输入公告列表页地址、项目编号、标段号，沿分页抓取原公告、延期公告和终止公告，按发布时间合并出该标段当前有效的投标截止时间。

另有**公告目录巡检**页：采购信息员输入公告目录 URL，首轮完整巡检只建立 SQLite 基准，此后按规范化详情 URL 比对，只列出新增公告的标题与来源。

应用使用 Python FastAPI，连同本地公告示例站通过 Docker Compose 启动。示例站为纯本地数据，**构建镜像后整个演示不需要访问互联网**。

## 启动

```bash
docker compose up --build
```

- 核验工具：<http://localhost:8000>
- 目录巡检：<http://localhost:8000/patrol>
- 本地公告示例站：<http://localhost:8001/notices?page=1>
- 可切换的巡检示例目录：<http://localhost:8001/patrol/notices?page=1>
- OpenAPI：<http://localhost:8000/docs>

首次启动会下载 Python 镜像与依赖；镜像构建完成后，核验、翻页、查看来源链接都在本机完成，可断网演示。

停止：

```bash
docker compose down
```

巡检基准保存在命名卷 `patrol-data` 中的 SQLite 文件（容器内 `/data/patrol.sqlite3`），停止或重启容器都不会丢失。如需清空基准，执行 `docker compose down -v`。

## 演示用例

首页已提供一键示例：

| 用例 | 项目编号 | 标段 | 预期 |
| --- | --- | --- | --- |
| 投标进行中（已延期） | `DEMO-2026-001` | `02` | 有效截止时间 `2026-11-12 09:30`，来源为第 2 页延期公告 |
| 已终止 | `DEMO-2026-001` | `01` | 状态“已终止”，**不显示有效截止时间**；时间线保留原公告、延期、终止三次变化及各自来源 |
| 不同编号格式 | `DEMO-2026-002` | `A` | 有效截止时间 `2026-11-25 14:00`；A 包的成交结果公告不改变截止时间 |

示例数据故意分布在第 1、2、3 页：`DEMO-2026-001` 的原公告在第 1 页，01 标段延期在第 2 页，终止在第 3 页；同项目 02 标段也有自己的公告，核对 01 标段时不会被混入。

示例站也可以在宿主机通过 <http://localhost:8001/notices?page=1> 直接浏览。工具内预填示例地址 `http://localhost:8001/notices?page=1`；即使应用与示例站分处不同容器，工具也能识别这个公开地址并转到容器内网抓取。核验结果中的所有来源链接会自动转成 `http://localhost:8000/demo/...` 代理链接，因此浏览器也可直接打开。

## 核验规则

1. **分页发现**：从列表页开始，沿 `rel=next`、分页器内的页码/下一页链接继续抓取，直到没有更多页或达到安全上限。
2. **精确匹配标段**：只有详情页中项目编号和目标标段号同时匹配才纳入合并。列表页有明确项目/标段信息时会先排除其他项目和其他标段，详情页仍会再次校验，避免混入同项目其他标段。
3. **按发布时间排序**：将命中的原公告、延期/更正公告、终止公告按详情页发布时间合并。
4. **只应用明确修改**：延期公告只有载明新的投标截止时间时才替换旧时间；页面只是引用旧时间、或只说“另行通知”而没有新时间时，结论为“无法判定”，不会把旧时间继续当作有效时间。
   - 同时支持“原时间……现延期至……”“……变更为……”“变更后：……”等写法，避免把“原时间”误当新时间，也不会把开标时间误当投标截止时间。
5. **终止优先**：一旦终止公告发布，状态固定为“已终止（不再接受投标）”，有效截止时间为空，旧时间只出现在历史时间线中并明确标注失效。
6. **失败即无法判定**：列表页、分页页、候选详情页抓取失败，详情页关键字段无法解析，缺少原公告，或相关公告缺少发布时间导致无法排序时，页面显示“无法判定”和失败/检索地址，并置空有效截止时间。**不会沿用之前的查询结果**。
7. **无缓存**：每次查询都实时重新抓取，不保存、不读取旧结论。

其他公告（如成交结果公告）可以出现在命中的公告列表中，但不会改变标段状态或截止时间。

## 目录巡检规则

1. **沿同站分页读取**：从输入的目录页开始，沿 `rel=next`、页码和分页器内的“下一页”链接继续读取，并逐条读取同站详情页。站外链接不会跟进。
2. **规范化详情 URL**：比对键统一 scheme/host 大小写、去掉默认端口、片段和追踪参数（如 `utm_*`），排序其余查询参数并去掉路径末尾斜杠。URL 中的公告 ID 等查询值保留，因此同一条公告跨页出现、带不同追踪参数链接时也只算一条。
3. **首次完整巡检只建基准**：第一次成功的完整巡检把全部公告写入 SQLite 基准，返回“基准已建立”，不列任何新增。
4. **只报基准之外**：后续巡检只在基准中不存在的规范化 URL 报告新增，附标题和来源链接；已报过的公告不会重复出现，即使旧公告因新公告插入而换到别的页。
5. **失败即停**：任一目录页或详情页读取失败、跳转站外、无法解析标题，或超过翻页/详情数量上限时，本轮整体记为失败。页面列出每个失败地址与阶段（分页读取/详情读取），**不报告新增、不修改公告基准**，方便先修复再重试。
6. **重试补报**：失败轮不会把已读到的公告写入基准；下一次成功巡检仍与上一次完整基准比较，因此失败期间发布的新公告会在重试成功后补报。
7. **并发只报一次**：基准比对在 SQLite `BEGIN IMMEDIATE` 事务内完成，多个巡检同时结束也只有一个请求能把某条新公告写入并报告，其余请求看到的是更新后的基准。
8. **基准持久化**：基准存在 SQLite 文件中，容器重启后仍可用。

### 示例场景

巡检示例目录可随时切换场景，用来演示上述规则：

| 场景 | 变化 | 预期 |
| --- | --- | --- |
| 初始基线 | 8 条公告，共 3 页 | 首轮“基准已建立”，不报新增 |
| 新增 1 条 | 顶部多 1 条 | 只报这 1 条；再巡检无新增 |
| 新增 4 条 · 旧公告换页 | 顶部插入 4 条，旧公告全部后移 | 只报 4 条新公告，旧公告不误报 |
| 同公告跨页重复 | 1 条新公告同时在第 1、2 页 | 只报 1 条 |
| 第 2 页读取失败 | 新增 1 条，但第 2 页返回 503 | 显示失败地址，不报新增、基准不变 |
| 详情读取失败 | 新增 1 条，但其详情返回 503 | 显示失败地址，不报新增、基准不变 |

失败场景切回“新增 1 条”后再次巡检，即可看到补报。

## 巡检 JSON API

```bash
curl -G http://localhost:8000/api/patrol \
  --data-urlencode 'list_url=http://localhost:8001/patrol/notices?page=1'
```

也支持 `POST /api/patrol`：

```json
{ "list_url": "http://localhost:8001/patrol/notices?page=1" }
```

关键返回字段：

- `status`：`baseline`（首轮建基准）/ `new`（有新增）/ `no_new`（无新增）/ `failed`（本轮未完成）/ `invalid`（地址无效）
- `new_notices`：本轮新增公告的 `title` 和 `url`（已转为浏览器可打开的 `/demo` 代理地址）
- `failures`：失败地址、原因和阶段，失败轮一定为空的新增清单
- `baseline_count` / `baseline`：当前基准条数与最近巡检状态
- `recent_additions`：该目录历次报告的新增记录（最多 20 条）

## JSON API

```bash
curl -G http://localhost:8000/api/check \
  --data-urlencode 'list_url=http://localhost:8001/notices?page=1' \
  --data-urlencode 'project_no=DEMO-2026-001' \
  --data-urlencode 'section_no=01'
```

也支持 `POST /api/check`：

```json
{
  "list_url": "http://localhost:8001/notices?page=1",
  "project_no": "DEMO-2026-001",
  "section_no": "01"
}
```

关键返回字段：

- `status`：`ongoing` / `extended` / `terminated` / `unknown`
- `determinable`：是否有足够证据形成结论
- `effective_deadline`：当前有效截止时间；终止或无法判定时为 `null`
- `deadline_source_url`：当前结论来源链接
- `changes`：按发布时间排列的变化记录，每条都带 `url`
- `failures`：抓取/解析失败地址及原因
- `notices`：命中的目标标段公告（不包含其他标段）

## 本地测试

不启动容器也可运行解析与合并规则测试（需要先安装 `requirements.txt`）：

```bash
python -m unittest discover -s tests -v
```

测试使用 `httpx.MockTransport`，覆盖跨页、延期替换、终止失效、同项目其他标段隔离、详情页失败、缺少原公告和“无新时间的延期”等场景。

巡检测试使用临时 SQLite 文件和同样的内存传输，覆盖首轮建基准、新增报告、旧公告换页、跨页重复、URL 规范化、分页/详情失败不改基准、失败后重试补报和并发只报一次等场景。

## 边界与限制

- 只抓取 HTTP/HTTPS 的 HTML 页面；链接限定在输入列表页同一站点（scheme + host），不会跟随站外跳转。
- 单次查询设置列表页/详情页数量和响应大小上限，避免误抓大型站点；超过上限时结论为“无法判定”而不是猜测。巡检同样受 `PATROL_MAX_PAGES`（默认 60）和 `PATROL_MAX_DETAILS`（默认 1500）约束，超过上限的轮次视为未完成，不改基准。
- 不处理需要登录、验证码、JavaScript 动态渲染的公告站。
- 日期按页面原始时区文本解析（示例为北京时间），不进行时区换算。
- 巡检识别的是“目录里出现了基准中没有的详情 URL”；已在基准中的公告若只改标题仍视为同一条，不重复报告。
- 示例站数据均为虚构，不代表任何真实采购项目。
